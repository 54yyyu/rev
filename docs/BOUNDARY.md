# System One 类模型的能力边界 — 实测

> **实验记录，按时间顺序写成（2026-09-20 至 09-21），rev 就是从这里长出来的。**
> 文中提到的脚本（`test_paste.py`、`harness.py` 等）原在 `misc/system-one-boundary/`，
> 依赖已删除的 `laya_mlx`，已于 2026-09-21 删除。现在复现用 `bench/`：
> `usecases.py`（剪贴板、风险闸门、日历、邮件）、`jevbench.py`、`speed.py`、`orders.py`。
> 后面章节的结论会推翻前面的，以 README.md 和 DECISIONS.md 为准。

「System One」指这一类只做选择、不生成文本的决策模型：TypeSafe 的 Jev、
Convai 的 Laya、SemIf/Qwen3.5、cua-s1、kev 等等。本文测的是**这一类能做什么、
从哪里开始崩**，以及**换模型能把边界推到哪**。

测过的模型：
- `aac6fef/laya-multilingual-mlx`（Convai Laya, 322M）— 第一至八节的主角，现已删除
- `Qwen/Qwen3.5-0.8B / 2B / 4B` 走 SemIf 的直接读 logits 方法 — 第九、十节
- Jev 1.13.0 的数字来自 JevBench v1.2.5，我们没有 API，未自测

三个真实任务（剪贴板粘贴、邮件筛选、日历实体挑选，全部用本机真实数据），
外加更早的 Pong / 文献筛选 / 国际象棋三个探索。

> 注意：第一至八节的结论基于 Laya，其中**两条在第九、十节被推翻**
> （「指认不行」和「选项 >20 就崩」）。读的时候从第九节的修正往回看。

## 一、边界地图

### ✅ 可靠（>90%，可自动执行）

| 任务 | 成绩 | 形状 |
|---|---:|---|
| Pong 方向判断（"球在上方" → UP） | 95–100% | 3 选项，一句话状态，单步关系推理 |

**唯一进入这一档的，是"一个关系词 → 一个动作"的映射。**

### ⚠️ 勉强（赢过随机，但赢不过或仅微弱赢过傻baseline）

| 任务 | 模型 | 傻baseline | 差距 |
|---|---:|---:|---|
| 剪贴板粘贴，n=5（带类型描述） | 0.825 | 0.200 (随机) | 4.1x |
| 剪贴板粘贴，n=8 | 0.700 | 0.125 | 5.6x |
| 剪贴板粘贴，n=20 | 0.625 | 0.050 | 12x |
| 口语填充词删除 | 0.756 | **0.722**（词表） | +3.4pt，n=90 不显著 |
| 邮件"是不是营销"（含正文） | AUC 0.793 | **0.754**（发件人正则） | +0.04 |
| 文献筛选 WSS@95（临床） | 0.25 | 0（随机顺序） | 发表系统在 0.3–0.7 |

**这一档的共同点：能用，但一个正则或词表能做到八九成，模型带来的增量在噪声边缘。**

### ❌ 失败（等于或低于随机）

| 任务 | 成绩 | 说明 |
|---|---:|---|
| 邮件"需要行动吗" | **AUC 0.176** | 标题写着 "Action Requested" 的那封得 **0.000** |
| 逐条判断"这是邮箱吗" | — | API key `sk-apikey-...` 对**每个**类型问题都返回 **p=1.00** |
| 数字比较（Pong numeric） | **0%** | 60/60 全选 STAY，低于 33% 随机线 |
| 文献筛选"是不是实证研究" | AUC 0.385 | 把综述排在实证研究前面 |
| 剪贴板 n=40（原文做描述） | 0.167 | 接近崩溃 |
| 国际象棋 | ~700 Elo | 20 局里 15 局三次重复和棋，无跨步记忆 |

## 二、六条实测规律

都在多个任务上重复验证过，不是单次观察。

**1. 决策相关的信息必须放 `state`，而且放最后。**
放进 `instructions` 会崩：剪贴板任务 n=5 从 0.650 掉到 0.250。

**2. 多余的从句会伤，但"多余"要看是否携带信号。**
- 伤：Pong 加两个从句 100% → 63.8%；screening 加摘要 AUC 0.763 → 0.641；口语清理加上下文 AUC 0.732 → 0.582
- 帮：邮件加正文 AUC 0.653 → 0.793（因为营销话术本身就在正文里）

判据不是"长短"，是**这段文字里有没有判据**。

**3. 选项要用「类型描述」，不要用原文。**
剪贴板 n=8：原文 0.400 → 类型描述 **0.700**。
把 `marcus@anything.com` 换成 `An email address.`，让它做语义匹配而不是格式识别。

**4. 选项数 ≤20，>30 崩溃。**
这也是 Jev 明确强于 Laya 的一项（Banking77: Jev 0.870 / Laya 0.425）。如果要做高基数选择，得用 Jev 或先用代码预筛。

**5. 有些看起来完全合理的问题会整个反过来。**
"需要行动吗" AUC 0.176、"是不是实证研究" AUC 0.385。**光看输出发现不了**——它照样给你一个 0 到 1 的数。

**6. 标定能让它诚实，但不能让它变准。**
screening 上 ECE 0.068 → 0.019，reliability diagram 对得很齐。但分数从不超过 0.5，阈值 0.30 时召回只有 9.5%。它诚实地说"我不知道"。

## 三、可操作的结论

**上线前必须做的一件事：拿标注数据量每一个问题的 AUC。**

这是规律 5 的直接后果。一个问题可能是反的，而你从输出上完全看不出来。没有 AUC 就不要用。

**什么时候可以信到自动执行：**
1. 是选择，不是生成（它 output token 恒为 0）
2. 候选由代码观察得来，模型无法捏造
3. 候选 ≤ 20，且每个有类型描述
4. 语义判断，不涉及数字比较
5. 状态一到两句话，判据在最后
6. 该问题的 AUC 已实测 > 0.8
7. 错了能撤销

**安全红线：永远不要让它判断"这是不是敏感信息"。**
实测 API key 对每个类型问题都是 p=1.00。密钥、密码这类必须用代码规则排除在候选之外，不进模型。

## 四、三个具体场景的判决

| 场景 | 判决 |
|---|---|
| **剪贴板粘贴** | 可做，但必须：代码按类型预筛到 ≤8 个候选 + 用类型描述 + 密钥类硬排除。本地 12ms。 |
| **口语清理（删填充词）** | **不值得。** 词表 0.722 vs 模型 0.756，且模型在自我纠正（`Wednesday. Oh sorry, no` → 0.014）和重复（`the the` → 0.207）上完全失败——正是词表做不了、你最需要的那部分。 |
| **邮件筛选** | **不要用它判断重要性。** 唯一能用的问题是"是不是营销"（AUC 0.793），而发件人正则就有 0.754。增量不值得引入一个会自信说错的组件。 |

## 五、重要更新：允许弃权后，结论要改

前面所有数字都是"强迫它必须选"的结果。cua-s1 的指标集（coverage / selective_accuracy /
abstention_rate）指出这低估了可用性：真正该问的不是"它总体多准"，而是**"它有把握的时候
多准、以及那部分占多少"**。

重测剪贴板任务（类型描述，每格 120 次）：

| 选项数 | 强制选择准确率 | 达到 90% selective accuracy 的门槛 | 该门槛下的 coverage |
|---:|---:|---:|---:|
| 5  | 0.817 | 0.75 | **63%** |
| 8  | 0.742 | 0.88 | **42%** |
| 12 | 0.625 | 0.88 | 28% |
| 20 | 0.533 | 0.98 | 7% |

**confidence 是真信号。** n=5 时 selective accuracy 随门槛单调上升 0.817 → 0.888 → 0.957
→ 1.000。这跟 screening 里"分数永不超过 0.5"是两回事：那里是没有区分度，这里有。

**真正的边界在 n≈12 到 20 之间，而且是 confidence 先失效。**
n=20 时提高门槛不再改善准确率（0.667 → 0.660 → 0.643），说明置信度已经不携带信息。
所以"选项 ≤20"这条要改成：**选项 ≤8 且用 confidence 门控**。

### 对产品的意思

剪贴板粘贴的正确形态不是"自动粘贴"，而是：

    confidence ≥ 0.88  →  直接粘（覆盖约 4 成，准确率 ~90%）
    confidence <  0.88  →  弹出候选列表让人选（其余 6 成）

这比"每次都猜"和"每次都问"都好。参考 Jev-cu 上线用的那套：
`minConfidence 0.5 / stopConfidence 0.3 / riskConfirm 0.2`——注意 risk 门槛只有 0.2，
因为误删误发的代价远大于多问一次。我们的数据说 0.5 偏松（n=8 时只有 0.772），
要 90% 得提到 0.88。

### 这条也适用于回头看 screening

screening 那个"标定后诚实但分数不过 0.5"的结论，在弃权框架下应该重测 coverage 与
selective accuracy 再下判断。当时用单一 accuracy 衡量，把这个信息压掉了。

## 七、技术迁移实验（来自 Jev-cu / cua-s1 / macbrow）

从那三个 codebase 抄了三个手法，在真实数据上对测。

### 手法清单

| 来源 | 手法 | 结果 |
|---|---|---|
| Jev-cu | 选项 key 用无意义编号，描述带类型前缀 (`AXButton: Submit`) | **有效** |
| cua-s1 | 把弃权做成一个显式选项（`skip` / `unsure`），而不只是卡阈值 | **看任务**，见下 |
| Jev-cu | 请求放 `instructions` 而不是 `state` | **有害**，我们的规律成立 |

### 邮件筛选：从"别用"翻盘成"能用"

| 方案 | AUC | recall@20% | recall@40% |
|---|---:|---:|---:|
| 发件人正则 baseline | 0.754 | 0.29 | 0.57 |
| M1 noul「是不是营销」（旧最佳） | 0.793 | 0.57 | 0.71 |
| M2 Choice 分类 + 类型描述 | 0.833 | 0.57 | 0.86 |
| **M3 = M2 + 显式 unsure 选项** | **0.878** | **0.71** | **1.00** |
| M4 = M2 但请求放 instructions | 0.784 | 0.43 | 0.86 |

**M3 的 recall@40% = 1.00**：排序后只看前 40%（54 封里 22 封），7 封重要的一封不漏。
这推翻了第四节"邮件筛选不要用"的判决——**换成分类 + 弃权选项之后是能用的**。

关键不是 noul 换 Choice，而是**让选项带类型描述**（跟剪贴板任务同一条规律），
再加一个 unsure 让不确定的概率有地方去。

### pyapple 式实体挑选：不行

「用户说一句话 → 从检索到的候选里挑那个具体条目」，用真实日历（27 个日程）测：

| 候选数 | 无 unsure | 有 unsure |
|---:|---:|---:|
| 5 | 0.646 | 0.479 |
| 10 | 0.521 | 0.438 |
| 27 | 0.354 | 0.271 |

**弃权也救不了**：n=27 门槛提到 0.8，selective accuracy 只有 0.40，置信度不携带信息。

### 由此得到最重要的一条区分

**归类可以，指认不行。**

- 「这封邮件属于哪一类？」候选是**语义类别**，彼此结构不同 → AUC 0.878
- 「这句话指的是 27 个日程里的哪一个？」候选是**具体实体**，彼此形态相似 → 0.354

剪贴板那个之所以能用，也是因为它实质上是归类（"Email address" 对 "An email address."），
不是指认。一旦要它在多个相似的具体条目之间分辨（三门都叫 `(Audit)` 的课、两节
`7.81 Systems Biology lec`），它就塌了。

**对 pyapple 的意思：检索和挑选都交给代码**（字符串匹配、日期过滤、模糊搜索），
模型只做「这个请求属于哪一类操作」这层路由。

### unsure 选项不是万能的

邮件 +0.045，实体挑选 −0.08 到 −0.17。差别在于**弃权是不是一个合法答案**：
邮件里"看不出是哪类"真实存在；实体挑选里答案一定在候选中，unsure 只会分走概率。

## 八、最大的一个技术发现：选项的 key 不要放内容

从 Jev-cu 源码里抄来的写法：

```js
criteria[`i${c.index}`] = sanitizeLabel(`${c.role}: ${c.label}`)
```

选项的 **key 是无意义编号**，内容全部放在描述里。我们之前一直把内容当 key
（`criteria = {"marcus@anything.com": "An email address."}`）。

同一批题、同样的描述，只改 key：

| 选项数 | 干扰项 | key = 原文 | key = 编号 | 差 |
|---:|---|---:|---:|---:|
| 8 | 易 | 0.680 | **0.960** | +0.28 |
| 8 | 难（同类型干扰） | 0.600 | **0.880** | +0.28 |
| 20 | 易 | 0.600 | **0.980** | +0.38 |
| 20 | 难 | 0.240 | **0.720** | +0.48 |

**这推翻了第二节第 4 条「选项 ≤20，>30 崩溃」。** 那个崩溃是把内容塞进 key 造成的
假象：Laya 在每个选项自己的 `[MASK]` 上打分，key 里的原文既吃掉 `head_max_len`
预算又和描述互相干扰。换成编号之后，n=20 的困难条件从 0.240 回到 0.720。

修正后的规则：**选项 key 用 `o0/o1/o2`，所有内容写进描述，描述以类型开头。**

注意日历实体挑选那个任务本来就用的编号 key，成绩依然只有 0.45–0.67，
所以第七节「归类可以、指认不行」的结论不受影响。

## 九、换模型实测：SemIf (Qwen3.5-4B) vs Laya，同一套 258 道题

JevBench 说 Laya 的 Intelligence 只有 63.2、在 21 个系统里排第 17，于是直接对测。
SemIf 自带 MLX backend，在这台 Mac 上原生跑。

| 任务 | Laya 322M | SemIf 4B (8bit) | SemIf 4B (4bit) |
|---|---:|---:|---:|
| 剪贴板 n=5 | 1.000 | 1.000 | 1.000 |
| 剪贴板 n=8 | 0.925 | **1.000** | **1.000** |
| 剪贴板 n=12 | 0.900 | **1.000** | **1.000** |
| 日历指认 n=5 | 0.667 | **1.000** | **1.000** |
| 日历指认 n=10 | 0.524 | **1.000** | **1.000** |
| 邮件 AUC | 0.878 | **0.970** | **0.967** |
| 邮件 recall@20% | 0.71 | **1.00** | **1.00** |

### 这推翻了第七节最重要的那条结论

第七节写的「**归类可以，指认不行**」——日历实体挑选 Laya 只有 0.354–0.667，我据此
断言这类模型做不了"从相似的具体条目里指认一个"。

**SemIf 在同样的题上是满分。** 那是 Laya 的天花板，不是这一类的天花板。

同理第二节「选项 ≤8」那条也要再放宽：Laya 换成编号 key 后 n=20 能到 0.72–0.98，
SemIf 在 n≤16 全满分（它硬性只支持 16 个选项）。

### 代价

| | Laya 322M | SemIf Qwen3.5-4B 4bit |
|---|---:|---:|
| 每题耗时 | **0.02 s** | 0.87 s (p95 1.23 s) |
| 磁盘 | 1.3 G | 8.7 G + 771 M |
| 进程峰值 RSS | ~0.7 G | 0.94 G |
| 选项上限 | 编号 key 后 ≥20 | **16（硬限制）** |

**慢 43 倍**是主要代价。内存反而差别不大（MLX 统一内存，4bit 下 RSS 0.94 G）。

4bit 相对 8bit 几乎无损（邮件 AUC 0.970 → 0.967，其余全部相同），所以没有理由用 8bit。

### 结论

- 需要**准确**的场景（剪贴板、邮件、实体挑选）→ SemIf 4bit
- 需要**每秒几十次**的场景（Pong 那种实时循环）→ 只有 Laya 能做，但它在真实任务上不够准
- SemIf 的 16 选项上限意味着高基数场景仍需代码先做粗筛

## 十、尺寸扫描：2B 是甜点

SemIf 的 MLX 后端只认 `model_type == "qwen3_5"`，换不了别家小模型，但 Qwen3.5
本身有 0.8B / 2B / 4B。同一套 258 题，全部 4-bit：

| | Laya 322M | Qwen3.5-0.8B | **Qwen3.5-2B** | Qwen3.5-4B |
|---|---:|---:|---:|---:|
| 剪贴板 n=5 | 1.000 | 0.750 | **1.000** | 1.000 |
| 剪贴板 n=8 | 0.925 | 0.425 | **0.975** | 1.000 |
| 剪贴板 n=12 | 0.900 | 0.325 | **1.000** | 1.000 |
| 日历指认 n=5 | 0.667 | 0.833 | **0.976** | 1.000 |
| 日历指认 n=10 | 0.524 | 0.500 | **0.929** | 1.000 |
| 邮件 AUC | 0.878 | 0.824 | **0.909** | 0.967 |
| 每题耗时 | 0.02 s | 0.20 s | **0.44 s** | 0.95 s |
| 磁盘 (BF16) | 1.3 G | 1.6 G | **4.3 G** | 8.7 G |

**0.8B 会塌**：剪贴板 n=8 只有 0.425、n=12 只有 0.325，比 Laya 还差。所以"更小更好"
到 2B 为止，再小就没有了。

**2B 是推荐点**：相对 4B 磁盘减半、速度快一倍，准确率只在邮件那一项有可见差距
（0.909 vs 0.967）；相对 Laya 则是日历指认 0.52 → 0.93 的质变。

一个成本上的注意：`--mlx-bits 4` 是**在内存里量化**，磁盘上仍然是 BF16 原始
checkpoint，所以 2B 占 4.3 G 而不是 1.2 G。要省磁盘得预先转成 MLX 4bit 格式，
但 SemIf 要求用带 40 位 commit 的原始 revision，会破坏它的可复现性检查。

## 十一、pyapple 就绪度检查（Qwen3.5-2B）

### 中文缺口已关闭

Laya 在中文上栽得很惨（"否则我们就换供应商了" → churn 0.0087）。2B 用同一批真实
日历、同样的 12 个请求分别用中英文问：

| 候选数 | 英文 | 中文 |
|---:|---:|---:|
| 5 | 1.000 | 1.000 |
| 10 | 0.833 | 0.833 |
| 16 | 1.000 | 0.917 |
| **总计** | **0.944** (34/36) | **0.917** (33/36) |

差 1 题，噪声范围内。**中英文都可以用。**

### 可以用的

- 实体挑选（日历实测 0.93–0.98，中英文均可）— pyapple 的核心模式
- 剪贴板粘贴（0.975–1.000）
- 邮件排序（AUC 0.909，recall@40% = 1.00）

### 还没测、上线前必须补的

1. **>16 个候选**：SemIf 硬限制。真实 `search` 可能返回更多，必须代码先粗筛。
2. **其他 pyapple 面**：contacts / notes / messages / reminders 都没测。形状相同，
   大概率迁移得过去，但没有数字。
3. **写操作与风险判断**：全部测的是"读 + 选"。发消息、建日程、删除这类
   **一次做错就有代价**的操作，以及 Jev-cu 那套 `riskConfirm=0.2` 的风险打分，
   完全没测过。
4. **置信度在什么时候会失灵**：2B 在这些任务上准确率太高（~0.95+），
   压不出 confidence 崩掉的边界。真要靠阈值自动执行，得先找到它会自信出错的场景。

### 邮件那条要特别注意

AUC 0.909 看着不错，但 **recall@20% 只有 0.71**——只看排序前 20% 会漏掉 7 封里的 2 封。
它是个**排序器，不是过滤器**。产品上应该是"把前 40% 排前面"，不能是"后 60% 不用看"。

## 十二、写操作的风险判断（Qwen3.5-2B）

57 个请求（27 危险 / 30 安全），中英文混合，覆盖 pyapple 的写操作面。
判据：**离开本机、销毁数据、或不可撤销 → 必须人工确认**；纯本地且易撤销 → 可自动执行。
故意埋了双向陷阱：温和措辞的破坏性请求，以及吓人动词的安全请求。

### 直接问"危不危险"：完全无效

| 问法 | 准确率 | AUC | 危险召回 | 安全误拦 |
|---|---:|---:|---:|---:|
| Choice：safe vs confirm | 0.474 | 0.607 | 1.000 | **1.000** |
| Noul：是否不可撤销 | 0.509 | 0.717 | 1.000 | 0.933 |

召回 100% 毫无意义——它把安全操作也拦了 93–100%，等价于一个"全部拦下"的常量函数。

### 改成分类操作类型、风险由代码决定：可用

模型只答「这是哪种操作」（read / note_local / mark / send / delete / edit_other），
代码把 `send|delete|edit_other` 判为危险。

| 方案 | 准确率 | AUC | 危险召回 | 安全误拦 |
|---|---:|---:|---:|---:|
| 仅模型 | 0.930 | 0.935 | 0.926 (25/27) | 0.067 |
| **模型 + 含糊动词硬规则** | **0.965** | — | **1.000 (27/27)** | 0.067 |

又一次验证「别问判断，问归类，判断交给代码」。

### 漏判的两个，是同一个陷阱

```
"Tidy up my calendar for next week"   → 判成 note_local, p=0.99
"帮我把下周日程整理一下"                → 判成 note_local, p=0.97
```

**这正是烧掉 macbrow 的那句话**（被要求 "clean up my desktop"，结果把桌面所有文件挪走）。
模型把"整理 / tidy"读成无害的本地动作，而且是**自信地错**。

补救是一条代码规则，不是换 prompt：

```python
VAGUE = re.compile(r'tidy|clean\s*up|clear\s*out|organi[sz]e|sort\s*out|整理|清理|收拾', re.I)
if VAGUE.search(request): return CONFIRM   # 不交给模型
```

误拦的两个方向相反且无害：`Kill the reminder`、`Wipe my template`——吓人动词配安全操作。

### 但这套测试本身有个更重要的局限

上面测的是「从**请求文本**猜意图」。真实系统里根本不需要猜：
**代码知道自己要调的是 `calendar.delete` 还是 `reminders.create`。**

所以风险闸门的第一道应该是**按实际调用的工具**来判，模型只当第二意见
（用来拦住"工具看着安全但参数很危险"的情况，比如 `mail.move` 把整个收件箱搬走）。
本节的数字说明模型可以当第二意见，不能当第一道。

### 样本局限

57 条全部由我手写，埋的陷阱是我想得到的那些。真实使用中一定有我没想到的。
这些数字能证明"这个方案可行"，不能证明"这个方案安全"。

## 十三、Jev（TypeSafe 官方 API） vs 本地 Qwen3.5-2B

拿到 TypeSafe key 后，同一批题直接对打。

### 英文，228 题（剪贴板 120 + 日历 108）

| 任务 | n | 本地 2B | Jev |
|---|---:|---:|---:|
| 剪贴板 n=5 / 8 / 12 | 120 | 1.000 / 0.975 / 1.000 | **1.000** |
| 日历 n=5 / 10 / 16 | 108 | 0.972 / 0.917 / 0.944 | **1.000** |
| **全部** | 228 | 0.969 | **1.000** |

配对检验：2B 对 / Jev 错 **0** 次，2B 错 / Jev 对 **7** 次，**McNemar p = 0.016，显著**。
（对比 4B vs 2B 那次 p=0.062，那是噪声，这次是真差距。）

### 中英对照，72 题

| | 英文 | 中文 |
|---|---:|---:|
| 本地 2B | 0.972 | 0.972 |
| **Jev** | **1.000** | **1.000** |

文档明写 CJK 精度较低、要求"test on your own content"，但在这个任务上没兑现。
**限制**：日历标题本身是英文，只有查询是中文，所以测的是跨语言匹配而非中文内容理解。

### 速度与成本

| | p50 | p95 | 成本 |
|---|---:|---:|---:|
| Jev (api.typesafe.ai) | **0.325–0.338 s** | **0.381–0.410 s** | $0.021–0.023 / 千次 |
| 本地 2B (MLX 4bit) | 0.348 s | 0.592 s | $0 |

**速度打平**，Jev 的 p95 还更稳。这纠正一个常见误解：
**Jev 的卖点是"更准"，不是"更快"**——它快是相对 LLM 生成（官方 5.2 倍），
不是相对 Apple Silicon 上的本地小模型。

### 选择依据只剩隐私

准确度 Jev 赢且显著，速度打平，钱可忽略（每天 50 次 ≈ 每月三分钱）。
**本地唯一的优势是数据不出机器。**

| 场景 | 选谁 | 理由 |
|---|---|---|
| 剪贴板粘贴 | **本地** | 剪贴板随时可能有密钥/密码，事先不知道 |
| pyapple 个人数据 | **本地** | 邮件、日历、联系人 |
| 做成产品分发 | **本地** | 不必让用户申请 TypeSafe key |
| 自己跑不敏感的分析 | **Jev** | 不用 4.3 GB 权重和 venv，还更准 |

### Jev 不接受图片

官方原文：*"Images, audio, and video are not supported (yet)"*，
*"Pre-process non-text inputs into text or structured fields"*。

所有 computer-use 实现都是用无障碍 API 把界面读成文字表，不发截图：

```js
criteria[`i${c.index}`] = `${c.role}: ${c.label}`   // Jev-cu
// { "i7": "AXButton: Previous Month", "i8": "AXTextField: Search" }
```

这正好说明第八节那个「编号 key + 类型描述」不是临时技巧，
**而是这一类系统表示界面的标准形式**。

## 十四、reflex 的 harness，以及在 JevBench 公开题上的自测

[reflex](https://github.com/kshetrajna12/reflex) 是第三个实现，和 SemIf 一样
**用冻结的 Qwen3.5**，差别全在 harness。它的消融记录极其完整，直接省掉我们很多弯路。

### 它测过、证明无效的（别再试）

| 试过的 | 结论 |
|---|---|
| 微调：四种 LoRA 配方 + 从 27B 蒸馏 | 全部"在像训练数据的题上赢，在长的模糊输入上失去判断力" |
| 超过两个选项顺序 | 无增益 |
| 措辞集成 | 无增益 |
| GEPA prompt 优化 | 不迁移 |
| **内容无关去偏 / PriDe** | **Rejected**：4B 几乎没有字母偏置可去，反而掉分 0.808→0.803 |
| disagreement 触发的推理级联 | 路由到的那个判官并不更好，p95 42 秒 |

**这毙掉了我先前的两条建议**（k=3 顺序、内容无关去偏），也说明"微调是唯一剩下的路"
这个判断大概率是错的。

### 它测过、有效的

字母式读出、Evidence/Criterion 框架、**两个不同选项顺序取平均**。

### 它的 weight-classes 表说明我们之前的测试太简单

| 外部集（300 题 ×4，从未训练） | 2B 两顺序 | 4B 两顺序 |
|---|---:|---:|
| mean | 0.628 | **0.810** |

| 公开基准 | standard | hard |
|---|---:|---:|
| 2B 两顺序 | 0.639 | 0.468 |
| 4B 两顺序 | **0.917** | **0.685** |

我们自己那套剪贴板/日历题上 2B = 0.969，是**天花板效应**。真有区分度的题上
2B 和 4B 差 18–28 个点，**远大于任何 harness 技巧**。

### 我们在 JevBench 公开题上的自测（Qwen3.5-2B，MLX 4-bit，SemIf prompt）

| 分层 | n | 单顺序 | 两顺序平均 | reflex 发表值 (2B) |
|---|---:|---:|---:|---|
| easy | 48 | 0.979 | **1.000** | 1.000 / 1.000 |
| hard | 111 | **0.450** | 0.387 | 0.405 / 0.468 |

**我们没能复现两顺序在 hard 上的增益，方向还相反。** 但 McNemar p=0.143，
111 题里差 7 道，**样本量不足以分辨**——既不能说他们错，也不能说我们错。

试了五种合并规则（概率平均 / logit 平均 / 几何平均 / 取最大 / 选更自信的分支），
全部落在 0.378–0.396，都不如单顺序的 0.450。

### 顺序敏感度实测

**hard 题上，把选项顺序倒过来，48% 的题会改答案**（一致率仅 0.523）。
easy 题上一致率 0.96。这解释了为什么小模型在难题上不可靠——
近一半的"判断"其实是位置决定的。

### disagreement 当弃权信号：easy 有用，hard 无用

| | 一致 | 准确率 | 分歧 | 准确率 |
|---|---:|---:|---:|---:|
| easy | 96% | **1.000** | 4% | 0.500 |
| hard | 52% | 0.517 | 48% | 0.377 |

easy 上它干净地挑出那 4% 需要人复核的题。hard 上即使两顺序一致也只有 0.517，
连续门控把覆盖率压到 14% 才换来 0.600——**没有任何门控能在 hard 上切出可信子集**。
这与 reflex 自己"disagreement 级联失败"的结论一致。

## 十五、自建 harness：让 2B 尽可能强

目标是**可泛化的提升**，不是把 harness 拟合到 JevBench 上。凡是用标签拟合的参数，
都在另一个数据层上拟合、在目标层上测。

### 结果

| 配置 | hard | 内存峰值 | 短题延迟 |
|---|---:|---:|---:|
| 2B 4-bit 单顺序（起点） | 0.450 | 3.49 GB | 285 ms |
| **2B 8-bit 单顺序** | **0.541** | 4.36 GB | 275 ms |
| 2B 8-bit + 两顺序 + yes 偏移 | **0.550** | 4.36 GB | ~550 ms |
| *对照：4B 4-bit 单顺序* | *0.595* | *5.00 GB* | *611 ms* |
| *对照：reflex 发表 2B bf16 两顺序* | *0.468* | | |

**净提升 +10 分，内存只多 0.87 GB，短题延迟不变。**

### ① 量化是最大的单一变量（+9.1 分，免费）

4-bit → 8-bit：hard 0.450 → 0.541，**延迟完全不变**（285 → 275 ms），
内存 +0.87 GB。这是所有 harness 技巧加起来都比不上的。

同一个发现解释了 4B 的差距：我们 4-bit 的 4B 是 0.595，reflex bf16 是 0.658。
**之前所有"这个模型不行"的判断，都有一部分是量化噪声。**

### ② 两顺序平均：只对 noul 有效，对 choice 有害

| | noul (38) | choice (73) |
|---|---:|---:|
| 单顺序 | 0.553 | **0.534** |
| 两顺序 | **0.605** | 0.507 |

4-bit 时它整体有害（0.450 → 0.387），8-bit 时净效果归零。
按题型分别选设置能到 ~0.568，**但那个选择是看着 hard 结果做的，等于过拟合，不报**。

### ③ yes 偏置：真实存在，可跨层迁移

2B 在 noul 上极度偏向 yes：**38 题里选了 32 次 yes**，真值是 17 yes / 21 no，
准确率恰好 0.500。

| 修正方式 | noul 准确率 | 是否泄漏 |
|---|---:|---|
| 不修 | 0.500 | — |
| 偏移在同一批题上拟合 | 0.632 | **泄漏，无效数字** |
| 偏移来自 hard 的另一半（交叉验证） | 0.610 | 干净 |
| **偏移来自 easy 层（不同题、不同家族）** | **0.579** | 干净，跨任务 |

easy 层测出 +1.219、hard 层 +1.757，方向一致量级相近 → **是模型+prompt 的属性，
不是题目的属性**，所以可以用任何一小批标注数据拟合后部署。

### ④ 内容无关去偏：不行（复现 reflex 的否决）

把 state 换成 "N/A" 或 "The information is not provided." 测纯先验再减掉：
0.500 → 0.474 / 0.368。**全部比基线差。**

原因：**空内容时的偏好和有内容时的偏好不是同一个东西**。这条对 4B 和 2B 都成立，
尽管 2B 的偏置大得多。所以"免标签去偏"这条路是死的，要修偏置就得有标注数据。

### ⑤ 选分支的上界

如果能完美地在两个顺序之间挑对，2B 4-bit 能到 **0.586**（几乎等于 4B 的 0.595）。
但试过的所有选择信号都不行：

| 信号 | 准确率 |
|---|---:|
| 基线（固定用顺序 a） | 0.450 |
| 选置信度更高的分支 | 0.387 |
| 选 margin 更大的 | 0.396 |
| 选熵更低的 | 0.405 |
| 选置信度更**低**的 | 0.459 |

**置信度是反向信号。** 这里还有 13 分的空间没人拿到。

### 推荐配置

```
模型     Qwen/Qwen3.5-2B
量化     --mlx-bits 8           ← 不要用 4-bit
顺序     noul 两顺序平均，choice 单顺序（此条待独立验证）
偏置     在自己任务的 ~50 条标注上拟合 yes/no 偏移后减掉
内存     峰值 4.36 GB，短题 275 ms
```

## 十六、三层完整成绩，以及 decider-2b 这个备选

### JevBench 公开题，三层

| | easy (48) | standard (72) | hard (111) |
|---|---:|---:|---:|
| **我们：冻结 Qwen3.5-2B, 8-bit, 自建 harness** | **1.000** | **0.764** | **0.550** |
| decider-2b v10（同基座，95 数据集微调 + RL） | 1.000 | **0.847** | 0.459 |
| Jev 1.13.0（官方，专门训练） | 1.000 | 0.986 | 0.730 |

**微调赢 standard（+8.3），冻结赢 hard（+9.1）。**

这同时解释了 reflex 和 decider 的矛盾：reflex 说"微调必然损害泛化"、decider 说
"held-out +11.3"——**两边都对，因为它们测的是不同形状**。微调能迁移到同一种任务
形状（分类），迁移不到另一种（长文档多跳推理）。

### 我们在 standard 上弱在哪

| family | n | 准确率 |
|---|---:|---:|
| extraction | 12 | **1.000** |
| ordinal | 12 | **1.000** |
| intent | 12 | 0.750 |
| policy | 12 | 0.667 |
| routing | 12 | 0.667 |
| adequacy | 12 | **0.500** |

抽取和序数判断满分；"回答是否充分"（adequacy）是抛硬币。

另：**两顺序平均和 yes 偏移在 standard 上完全无效**（三种配置都是 0.764），
只在 hard 那种高不确定性的题上有作用。

### decider-2b：记为备选，暂不换

[Mapika/decider-2b](https://huggingface.co/Mapika/decider-2b)，Apache-2.0，4.2 万下载。
同基座 Qwen3.5-2B-Base，约 95 个公开决策数据集微调 + 384 步 calibration-aware RL。

**不换的理由**：它在 hard 上比我们低 9 分，而我们实际任务上冻结 2B 已经 0.969–1.000，
换过去看不到收益，还多一份权重要维护。

**将来可能要换的理由**：我们的产品形态（剪贴板、邮件分类、日历指认）全是分类形状，
正是它的强项。如果哪天做出一个有区分度的分类任务、而冻结 2B 不够用，它是第一顺位。

**值得抄的工程设计**：
- **2–255 个选项**：≤10 个用 `(A)..(J)` 字符串渲染，>10 个改为每选项一个标签 token
  （我们 SemIf 卡在 16，reflex 卡在 26）
- `abstain_below=t` 内置弃权
- 拟合好的温度直接存进 `decider_config.json`
- TypeSafe 兼容的 `/v1/systemone`

## 十七、为什么 standard 只有 0.764：查了，不是 harness

decider-2b（微调）0.847 对我们 0.764，差 6 题。逐项排查已知的 harness 病症：

| 检查 | 结果 | 结论 |
|---|---|---|
| score 型是否丢了序数结构 | **12/12 满分** | 没问题 |
| noul 是否有 yes 偏置 | 选 11 no / 13 yes，真值 12/12 | **无偏置** |
| choice 是否有位置偏置 | 8,9,11,7,1（期望 7.2） | **无偏置** |
| state 扁平字符串 → 结构化对象 | 0.764 → **0.750** | **更差，否决** |

四项全部排除。失败集中在**验证类判断**：

```
"说出参考里的两个颜色"，参考 red and teal，回答 "red"   → 模型 yes (p=0.62)，真值 no
"返回含整数 3 的 JSON 数组"，回答 {"value":3}          → 模型 yes (p=0.96)，真值 no
```

模型一律**太宽松**。decider 在这类上强，是因为它的训练混合里有 RewardBench、
arena_pref 这类判断数据——**那是训练优势，不是 harness 优势**，换 harness 拿不到。

分家族：extraction 1.000、ordinal 1.000（这两项最接近我们的实际用途），
intent 0.750、policy 0.667、routing 0.667、adequacy 0.500。

## 十八、自建 harness（`harness.py`）

把三家的长处合起来，并验证与 SemIf 等价。

| 来自 | 采用的设计 |
|---|---|
| SemIf | Evidence/Criterion JSON prompt；一次前向读字母槽 logits；单 token 往返校验 + 答案边界不改变分词的校验 |
| decider | **宽标签空间**：不止 A–P，扫描词表里所有单字符可往返 token |
| reflex | 两个选项顺序取平均（**默认关闭**，实测只对 hard 的 noul 有用） |
| 本文实测 | 8-bit 量化（默认）；可选的 yes/no 偏移（需自己任务的 ~50 条标注） |

### 容量

```
SemIf     16 个选项（LETTERS = "ABCDEFGHIJKLMNOP"）
reflex    26 个（string.ascii_uppercase）
本 harness 101 个（A-Z + a-z + 0-9 + 希腊字母 + 符号，逐个校验）
decider   255 个（>10 时改为每选项一个标签 token）
```

### 正确性

与 SemIf 在重叠区间**逐题比对：40/40 同答案，概率最大差异 0.0000**。

真实日历指认任务（8-bit）：

| 候选数 | 准确率 | 随机 | 每题 |
|---:|---:|---:|---:|
| 8 | 0.852 | 0.125 | 368 ms |
| 16 | 0.889 | 0.062 | 605 ms |
| **27** | **0.852** | 0.037 | 902 ms |

**27 个选项不崩**，而 SemIf 在 >16 时直接拒绝运行。

### 一个值得记的 bug

第一版 harness 在 n=8 只有 0.222（接近随机）。原因是漏了
`apply_chat_template(..., enable_thinking=False)`——Qwen3.5 默认插入 thinking 段，
**最后一个位置就不再是答案字母该出现的地方**。

注意"答案边界不改变分词"那道校验**没能发现这个错误**，因为拼上字母后分词仍然一致，
错的是位置的语义而非分词。这类 bug 只有对照已知正确实现才查得出来。

## 十九、decider 的权重 + 我们的 harness

问题：微调过的 decider-2b 换上我们的 harness 会不会更强？

**我的预测是"不会"**，理由是 decider 在自己的 prompt 格式上微调
（`"Answer k: ("` 槽位 + `(A)..(J)` 渲染），我们用的是 SemIf 的
`{evidence, criterion, options}` JSON，格式完全不同。

**预测错了。**

| | easy | standard | hard |
|---|---:|---:|---:|
| decider-2b + **我们的 harness**（8-bit） | 1.000 | **0.861** | 0.459 → **0.477**（两顺序） |
| decider-2b + 它自己的 harness（官方发表） | 1.000 | 0.847 | 0.459 |

standard **+1.4**，hard 单顺序**完全一致**（0.459 = 0.459），加两顺序再 **+1.8**。
微调学到的东西**跨 prompt 格式迁移**，比预想的稳健得多。

### 四方完整对照

| | easy | standard | hard |
|---|---:|---:|---:|
| 冻结 Qwen3.5-2B + 我们的 harness | 1.000 | 0.764 | **0.550** |
| decider-2b + 我们的 harness | 1.000 | **0.861** | 0.477 |
| decider-2b + 它自己的 harness | 1.000 | 0.847 | 0.459 |
| Jev 1.13.0（官方） | 1.000 | 0.986 | 0.730 |

**格局不变，只是两边都被抬高了一点**：微调赢 standard（+9.7），冻结赢 hard（+7.3）。

两顺序平均对两个模型方向一致（冻结 0.541→0.550，decider 0.459→0.477），
比 4-bit 时那个混乱结果（0.450→0.387）可信得多——再次说明**当时的异常是量化噪声**。

### 工程记录

`mlx_lm` 不认 `model_type: qwen3_5_text`，但架构类就是 `Qwen3_5ForCausalLM`。
做一份 config 打过补丁的本地副本（权重用符号链接，不占额外磁盘）即可加载：

```bash
ln -s <snapshot>/model.safetensors decider_patched/
python -c "import json;c=json.load(open('<snapshot>/config.json'));c['model_type']='qwen3_5';json.dump(c,open('decider_patched/config.json','w'))"
semif-score --model ./decider_patched --revision local-v10 --mlx-bits 8 ...
```

8-bit 下权重 1.86 GB，与冻结 2B 完全相同（同尺寸同架构）。

### 逐题对照：微调买到了什么、赔掉了什么

同一批题、同一个 harness、都 8-bit 单顺序。

| | standard (72) | hard (111) |
|---|---|---|
| 只有冻结对 | 5（routing 3, extraction 1, adequacy 1；4/5 是 choice） | **21**（long_policy 8, temporal 3, ambiguous 3…；16/21 是 choice） |
| 只有微调对 | **12**（policy 4, adequacy 4, intent 2, routing 2；**8/12 是 noul**） | 12（multi_hop 3, adversarial 3, long_policy 2…） |
| 都错 | 5 | 39（temporal_numeric 9, judge_hard 8, multi_hop 7, long_policy 6） |

**微调买到的是短文本上的二元规则判断，赔掉的是长文档选择。**

样例（standard，微调独赢）：

```
"Policy: trial 用户可导出 CSV；PDF 需付费。Trial 用户请求 CSV。"
问：按此政策该请求允许吗？
  冻结  no  (p=0.53)   ← 错，而且基本在猜
  微调  yes (p=1.00)   ← 对
```

样例（hard，冻结独赢，2141 token 文档）：

```
  冻结  yes (p=0.73)   ← 对
  微调  no  (p=0.99)   ← 错，而且极度自信
```

### 最重要的一条：微调让置信度变得不可信

hard 层按输入长度切开：

| | 短题 <600 tok (n=66) | 长题 ≥1500 tok (n=36) |
|---|---:|---:|
| 冻结准确率 | 0.576 | 0.500 |
| 微调准确率 | 0.515 | 0.417 |
| 冻结错时平均置信度 | 0.705 | 0.635 |
| 微调错时平均置信度 | 0.842 | 0.764 |
| **冻结「错且 p>0.9」** | **9.1%** | **8.3%** |
| **微调「错且 p>0.9」** | **27.3%** | **25.0%** |

**微调把"自信地错"的概率变成 3 倍。**

这直接影响产品设计：我们定的架构是用 confidence 门控自动执行
（≥0.88 直接执行，否则交给人）。用 decider 的话，那道门会放进 3 倍多的错误答案
——**准确率更高，但门控更不安全**。要用它就必须重新拟合阈值，并且接受更低的覆盖率。

### 两边都救不了的

`temporal_numeric` 9 题全错、`judge_hard` 8 题全错、`multi_hop` 7 题全错。
这是类级边界，换模型换 harness 都无效——与 Jev 官方自己 temporal_numeric 仅 0.267 一致。
